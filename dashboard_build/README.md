# Mittal Group SAP dashboard

A live, multi-page dashboard on top of SAP S/4HANA Cloud OData CDS views. A small Python server (`backend/serve_dashboard.py`) calls SAP, caches the
result and serves the seven pages of `frontend/` (six data pages and one Summary page that combines five of them). There is no database and no build step: standard library only, Python 3.12.

```
dashboard_build/
  backend/    Python server, SAP access, lookup tables and the hand-edited data files (backend/data)
  frontend/   the seven pages (HTML, CSS and JavaScript in one file each) and the logo
  Dockerfile  Cloud Run image (copies backend and frontend)
  README.md
```

The menu (the same on every page) is in this order: Summary, Store Issue, Capital Issue, Store Stock, Pending PR, Pending Purchase Orders, PO Approval Pending, Pending Invoice Entry, Purchase, Price Variance, Payment Ageing (Store Issue first and Store Stock second, as the user asked on 21-Oct-2026; **Capital Issue was put right after Store Issue and given that name on 26-Oct-2026**, user: "Asset transiction ko Store Issue ke bagal me karo aur uska name Capital Issue ka rakho"; the page was first called Asset Transactions, the address `/asset`, the view and the code names (`asset_template.html`, `/api/asset`, `asset_compact`) kept the old name). The order is the `<nav class="nav">` line at the top of each page template; the table below is in the order the pages were built.

| Page | Menu tab | CDS view(s) | What it shows |
|---|---|---|---|
| `/summary` | Summary | the views of the pages below (no extra SAP call) | One card per page with only counts and INR, filtered by plant and date, and the full pages stacked under it |
| `/` | Pending PR | `YY1_STORE_PENDING_PR_CDS` | Purchase requisitions still to be ordered: ageing, plant and PO status, purchasing group, user, month and day wise, item list |

| `/po-approval` | PO Approval Pending | `YY1_PO_ITEM_SUPPLIER_CDS` | POs that are In Approval, with how long they have waited and the (likely) approver |
| `/invoice` | Pending Invoice Entry | `YY1_STORE_INVOICE_VL06_CDS` + the PO data of `/api/po` for the supplier name and the value | Supplier invoices entered as inbound deliveries (SAP monitor VL06) whose goods receipt (MIGO) is not posted yet: by supplier, department, plant, waiting time, month and day, with every item |

All views are read with the SAP communication user `POWERBI_USER_PRD` (basic auth). Everything is read-only.

## Run it on this PC

Double-click `..\Start_Live_Dashboard.bat` (or run `python serve_dashboard.py` in the `backend` folder). The dashboard opens at http://localhost:8765/.

SAP login on a local PC:

1. On the first start the server asks for the SAP user (Enter alone takes `POWERBI_USER_PRD`) and the password (typing is hidden).
2. After a successful login it saves them in **Windows Credential Manager** (target `MittalDashboard/SAP`, encrypted for this Windows user), so later starts do not ask.
3. If SAP rejects the saved password (HTTP 401) the saved login is removed and the server stops, so a wrong password is never retried on its own (account lock). Start again and type the current password.
4. The password is never written to a file, a log or the page. Do not paste it into chat or into any file of this project.

Options (`python serve_dashboard.py --help`):

| Option | Environment variable | Default | Meaning |
|---|---|---|---|
| `--port` | `PORT` | 8765 | Port to listen on |
| `--lan` | | off | Local PC only: let other PCs open `http://<this-pc-ip>:8765/` (no login) |
| `--base-url` | `SAP_BASE_URL` | Pending PR view | Base URL of the Pending PR view |
| `--ttl` | `CACHE_TTL` | 25 | Seconds to reuse the data of every view before asking SAP again (25, a little under the 30 s the pages ask again, so every check reads fresh data; see "Live refresh" below) |
| `--no-browser` | | off | Do not open the browser |
| | `SAP_USER`, `SAP_PASSWORD` | | SAP login (used on Cloud Run, from Secret Manager) |
| | `K_SERVICE` | | Set by Cloud Run; switches to cloud mode (listen on `0.0.0.0`, no prompt, login from the variables) |

## How it works

```
browser  --/api/*-->  serve_dashboard.py  --OData V2, basic auth-->  SAP S/4HANA Cloud
   ^                        |  cache + compact JSON
   '---- page (HTML) -------'
```

Browsers cannot call SAP directly (no CORS, and the password would sit in the page), so the server makes the calls and returns compact JSON.

* **`Sap` class** (`serve_dashboard.py`): one instance per view. It reads every page of the view (`$top 5000`, `$inlinecount=allpages`, the remaining
  pages in parallel with 4 workers) and keeps the result in memory (JSON + gzip).
  * Every query has a stable `$orderby` (the key of the view). Without it SAP skips and repeats rows between pages.
  * **Live refresh (24-Oct-2026, user: "dashboard ko 30 second me auto refresh, data update hota rahe")**: every view has a cache of 25 s (`--ttl`, a little under the 30 s of the page checks, otherwise every second check would be answered from the cache; the Refresh button re-reads at once, at most every 10 s, `MIN_REFRESH`).
    The pages ask their view every 30 s (`LIVE.every` in `frontend/live.js`) while they are open, and only then: **a view is read from SAP only when a page asks for it**, never when no page is open.
    A request that finds old data starts the read in the background and waits up to 6 s (`WAIT_FRESH`) for it, so the small views (Pending PR, Pending Invoice Entry) are fresh at every check; a big view (a read takes 10-25 s) answers with the old data at once and the next check gets the new data. Only one read of a view runs at a time.
    The server gives every payload a digest (`ETag`, the hash of the data without the read time) and the read time (`X-Fetched-At`). A page sends the digest it has (`If-None-Match`); when nothing changed the server answers **304** without the data and the page does not redraw (so scroll position, open tiles and filters stay), it only moves the "updated hh:mm" time. The Summary draws again only when one of its seven views changed.
    The goods issues read with the stock (about 300,000 rows, 60 calls) are read in full every 30 minutes (`FULL_EVERY`) and in between only the last 7 days are read (`consume_recent_query`, 1 call) and added to the last full state; a goods issue posted more than 7 days back shows in "last used" at the next full read. The other views are read in full each time (Issue 10 calls, PO 22, Purchase 8, Ageing 5, Stock 6, Pending PR and Invoice 1 each, about 50 calls a cycle).
    To lower the load on SAP, start with `--ttl 120` (or set `CACHE_TTL`); the pages still check every 30 s, they are just answered from the cache.
  * **Fast start: the data of the last run is kept on the disk** (29-Oct-2026, user: "Loading from SAP... 6 of 8 ready, refresh hone me bohot time ho raha hai"): after every read from SAP each view is saved to `backend/cache/<view>.cache` (local PC only, not in git, rebuilt by the dashboard itself; the state of the incremental goods-issue read is saved with the stock). A start of the dashboard on the **same day** with the **same program files** shows that data at once (the window says "Showing the data of the last run at once") and reads SAP again in the background, three views at a time, the biggest first (`warm()` in `serve_dashboard.py`); the Summary no longer waits for a cold read of all 8 views. A file from another day (the pages take today's date from the data) or from other program files (any edit of `serve_dashboard.py` / `pr_data.py` changes the version) is ignored, so the first start of a day and the first start after a code change still read SAP (about 20-30 s per big view, 5-6 views in parallel; it was 10 minutes and more when the PC was out of memory). A request that finds old data now waits only 2 s (`WAIT_FRESH`) for the new data and then answers with the old data at once; the page asks again after 30 s. Every read is written with its duration to `backend/server.log` (also what the window shows; `*.log` is not in git), e.g. `fetched 72,788 rows from SAP (YY1_PO_ITEM_SUPPLIER) + 34,901 (YY1_PO_ITEM_STATUS) in 27.1 s`: look there first when a start is slow. If SAP rejects the saved password the warm-up removes it from Windows Credential Manager (as before at start).
  * **Plant 1040 (Medal) is left out of the whole dashboard** (29-Oct-2026, user: "1040 plant ki details hata do sab jagah se"): `EXCLUDE_PLANTS = ('1040',)` in `backend/pr_data.py`. Every row of such a plant is dropped when a view is read from SAP (`Sap._refresh` for Pending PR, Store Issue, Purchase Orders, Store Stock, Purchase and Pending Invoice Entry; `asset_compact` for the Capital Issue transactions, because only one line of a transaction carries the plant; `load_stock_locations` skips the 1040 locations of `stock_locations.csv`), so no page, tile, total, filter, graph, PDF or CSV has it, and the Summary and Price Variance follow. The window / `server.log` says how many rows were left out (29-Oct-2026: PR 1, Store Issue 185, PO items 854, stock rows 2,028, Purchase 423, invoices 4, 21 asset transactions). To bring the plant back delete it from the tuple and restart. NOT removed because they are not rows of the plant: the Payment Ageing balances (vendor items have no plant, only a company code), Store Issue lines of the plants 1010 / 2010 / 2020 that are charged to cost centres 1040xxxxxx or to the departments "Medal" / "Craft Works (Medal)" (255 lines, Rs 1.06 L), and the names "Medal" in the lists of purchasing groups (118) and material groups (1753, 1759, 1638).
  * `query` may be a list of variants; if SAP answers 400 the next, simpler one is used (Store Issue falls back to a date-only filter).
  * `extra=[(base, entity, query[, fold])]` reads more views together with the main one and passes their rows to the compact function.
    With a `fold(state, rows)` function the extra rows are processed page by page and not kept in memory (used for the ~290,000 goods issue rows of the stock page; `Folded` holds the result).
  * After one 401 no view calls SAP again (`Sap.auth_failed`), so a bad login cannot lock the SAP user.
  * A network hiccup (timeout, connection reset) or a 502 / 503 / 504 from SAP is tried again up to 3 times (after 2 s and 4 s); 400, 401 and 403 are never retried.
  * An `extra` entry can be optional (`(base, entity, query, fold, True)`): if it cannot be read the view is served without it. The goods issues of the stock page are optional: without them the stock still shows and only "Not used for 5 months" is missing.
  * Any other error while preparing a view comes back as `{"error": ...}` with status 500 and is written with its traceback in the server window; it never drops the connection.
* **Server details:** a local server listens on `127.0.0.1` and on the IPv6 loopback `::1` (otherwise `localhost` waits about 2 seconds on every new connection, because it tries `::1` first). `HEAD` works. Every response carries `Content-Security-Policy` (pages are self-contained), `X-Frame-Options: SAMEORIGIN`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`; the logo is cached for a day, everything else is `no-store`.
* **Compact JSON** (`backend/pr_data.py`): each `*_compact` function turns SAP rows into arrays of numbers plus shared dictionaries (plants, users, units ...),
  so a page with 60,000 rows is a few MB gzipped. The row layouts are documented in the docstrings.
* **Pages** are templates with placeholders: `__USERS__` (user names), `__PGS__` (purchasing group names),
  `__MGS__` (material group names). The server fills them on every request, so **a template edit shows after a browser refresh; a change in a `.py` file needs a restart**.
* **API**: `/api/pr`, `/api/issue`, `/api/po`, `/api/stock`, `/api/purchase`, `/api/invoice`, `/api/ageing`, `/api/asset`, `/api/po-approval` (add `?refresh=1` to force SAP; they answer with `ETag` and `X-Fetched-At` and with 304 to a matching `If-None-Match`), `/healthz`, `/logo.png`, and the shared look and helpers `/ui.css`, `/ui.js` and `/live.js` (revalidated on every load, so an edit shows after a refresh).
  All responses are `no-store`; errors come back as `{"error": "..."}` and the page shows them next to the red status dot.

## Checking the dashboard

With the dashboard running, `python backend/check_data.py` (stdlib only) answers: does every page and API work, and what is still missing in the lookup tables:
purchasing groups and material groups without a name, user IDs without a name, reservation creators without a department, Store Issue lines without a department,
POs In Approval without a confirmed or likely approver, listed stock locations that hold no stock, and how old the data is. It exits with 1 when a page or an API fails.
Run it after changing `pr_data.py` or the CSV files, and before a deployment.

`python backend/export_po_datewise.py OUT.xlsx 2026-10-01 2026-10-31` (dashboard running) writes an Excel file of the purchase order items created in those dates, date wise, with the description and the three values (Total order value, Delivered value, Pending value in rupees) per item, a date wise summary and a summary by delivery status, both made with Excel formulas over the item list so they can be checked. The data is the live SAP data of `/api/po`. Note: with all items, the total also holds the "No GR" items (nothing left to deliver, nothing received), which SAP's own Purchase Order Items list does not show (₹17.73 Cr of 25 items in October 2026, mostly the STO PO 4800000585); they are shown on their own line of the status summary.

## Page rules

### Summary (`/summary`)
* The first tab of the menu. It adds no SAP call of its own: the browser reads the same `/api/*` data as the other pages and works the figures out with the **same rules as those pages** (copied from them, `prepPR`, `prepIssue`, `prepPO`, `buildApprovals`, `prepPurchase`, `prepInvoice`, `prepAsset`), so a figure here equals the figure on the page with the same filters.
* **One card under the other** (user, 24-Oct-2026: "Store Issue me heading ko line by line hi kro, side me kuch aur mat kro, ek ke niche ek kro"): the cards are in a single column, full width, never two side by side; the tiles of a card are in one row (4 across, 2 across on a phone) so the tiles line up from card to card. The menu is a little tighter (nine tabs) so it stays on one line on a normal screen.
* **Only numbers, as the user asked on 23-Oct-2026 ("only kaam ki cheezein, only count and INR")**: one small card per page, in the menu order (Store Issue, Capital Issue, Store Stock, Pending PR, Pending Purchase Orders, PO Approval Pending, Pending Invoice Entry, Purchase), each with 2 to 4 tiles that hold one number (a count or an amount in INR) and its name. No descriptions, no top-5 tables, no alert cards and no second row of headline tiles (they repeated the first tile of each card). The figure of all dates (and a short explanation where one is needed) is in the hover text of a tile.
* Tiles: Store Issue (net issue value, issue lines); Store Stock (stock value, in quality inspection, materials not used for 5 months and their value); Pending PR (pending items, net value, delivery date passed, older than 1 year); Pending Purchase Orders (value still to be delivered, purchase orders, PO items, net PO value); PO Approval Pending (POs In Approval, net value, waiting more than 30 days); Payment Ageing (To give / Dena hai and To get / Lena hai, in INR; `prepAgeing`, `calcAgeing`, it follows neither the plant nor the dates); Pending Invoice Entry (invoices, items, value approx., waiting over 7 days; the value is the delivery quantity at the PO price from `/api/po`, `calcInvoice`); Purchase (purchase value 101, reversal value 102, net, purchase orders); Capital Issue (acquisition value of types 100 + 120, acquisitions, MAL 1000 value, MCPL 2000 value; the plant filter picks the company, `prepAsset`, `calcAsset`).
* Filters: Plant and a date range (the whole current month at first; "Current month" resets it). Which date a page uses is in the hover text of the "Date from" label (PR creation date, posting date, PO creation date, delivery date); Store Stock is the stock of today and takes only the plant.
* **The other pages follow under the Summary, one after the other** (user, 21-Oct-2026: scroll on and Store Issue comes, then Store Stock, then Pending PR ...). Under the Summary come the full pages in the menu order: 2 Store Issue, 3 Capital Issue, 4 Store Stock, 5 Pending PR, 6 Pending Purchase Orders, 7 PO Approval Pending, 8 Pending Invoice Entry, 9 Purchase, 10 Price Variance, 11 Payment Ageing, each under a bar with its name, "Open full page" and "Top". Every page is the real page in an `<iframe>` (`?embed=1`), so it works exactly like the page itself; **since 25-Oct-2026 every page of the stack is folded to its bar** (button Show / Hide, or a click on the bar; what is open is remembered in the browser, key `spr-stack-open`) and a page loads only when it is opened, so the Summary is about 2,500 px long instead of 12,000+ and nothing is read from SAP for a folded page; a click on a menu tab opens that page, waits for the open pages above it to load and scrolls to it. Inside the Summary a page has no header, menu or footer of its own and its long lists have a fixed height. Print leaves the stacked pages out.
* Each card fills as its data arrives; a view that fails shows its error in its card.
* **Every tile is a link** that opens the details of the same tile on its page, with the plant and the dates chosen here carried over (see "Links between pages" below).

### Store Issue (`/issue`)
* Goods movements 201 (issue to a cost center) and 202 (reversal) since 1 Jan 2026. Quantity and value are positive for an issue and negative for a reversal.
* **Reversals (202) are shown on their own** (user, 24-Oct-2026: "Store Issue reverse bhi dikhao 202 mov", then "isko balance karo, minus karke"): the tiles **Issued (201) | Reversed (202) shown with a minus (-₹15,600) | Issue Materials | Cost centers** (the tooltip of the Reversed tile spells the balance out: Issued ₹1,64,40,727 - Reversed ₹15,600 = Net ₹1,64,25,127; the tooltip of Issued has the line count). * **Rate** of a material = net value in rupees / order quantity of its PO lines (document currency x the PO exchange rate), per material and unit, **one rate per PO date** (lines of one date averaged by quantity; a line worth less than 10% of the biggest line of that day, e.g. a free-of-charge item, is left out: Copper Cathode PO 4600000183 had two such lines at Rs 0.09 that would have halved its first rate). * **Profit and loss** (purchase price variance, nothing is sold here): the reference rate is the rate of the first PO date of the period. Per material and in total, by month, by material group.
